05 / DATA MODEL

A relationship tells Power BI which rows belong together.

Before you join two tables, check what one row means in each table, which columns match, and which table has one row for each match.

MODEL VIEW WHAT MATCHES? CHECK THE LINK

The Retail tables describe different things. Sales has one row for a Store, Department and Date. Features has one row for a Store and Date. Stores has one row for a Store. If you ignore that difference, Power BI can produce totals that look neat but are wrong.

Start by asking what one row describes

F

Features

One row = Store + Date. Temperature, fuel price, markdowns and holiday information.

S

Sales

One row = Store + Dept + Date. Weekly sales for one department.

D

Stores

One row = Store. Store type and size.

What should match?

Build and test the exercise relationship

1

Create the first Mixed Key

In Features data set, add a calculated column using the lesson's CONCATENATE([Store], [Date]) pattern.

You should see: a key value combining Store and Date.
Why: Store repeats across dates, so Store alone cannot identify a Features row.
2

Create the matching key

Make the same named key in sales data-set, then inspect both columns before relating them.

You should see: matching text patterns on both sides.
Why: Power BI can only match rows when the values and types agree.
3

Check the key before drawing the line

Look for different types, missing separators or two different combinations producing the same text.

You should see: a documented key assumption and a known unique/repeated side.
Why: a key that is not unique can join the wrong rows.
4

Open Model view

Remove the automatically inferred Features–Stores connection if it is not the link you intend. Drag the lesson key from Features to Sales.

You should see: a relationship line between the tables through the Mixed Key.
Why: this exercise matches Store + Date context to Sales rows.
5

Choose the relationship settings

Check the one-to-many setting (1 → *) and the filter direction. Do not leave Both-direction filtering on without a reason.

You should see: the relationship dialogue reflecting the chosen options.
Why: a filter can travel through more than one route and change a total you did not mean to change.
6

Test the link with a chart

Use Store and Date in a simple chart. Select a store and check the rows and totals that change.

You should see: filtering changes the intended visual and does not silently change unrelated totals.
Why: the line in Model view is not enough; the filter must behave as expected.
For this exercise: use the Mixed Key because the LMS asks for it. In other work, check key uniqueness and use clear separators before joining tables.
Check your model before building a report page
  1. What does one row represent in each table?
  2. Which side should be unique?
  3. Which fields make the intended match?
  4. What filter path should a Store selection follow?

Check: explain the relationship in ordinary words before trusting a total made through it.

Code Institute LMS exercise: build the lesson model

The LMS model task uses the tables you imported. Create and inspect the keys before drawing the relationship.

Make the Features–Sales link

  1. In Features data set, create the DAX calculated column Mixed Key = CONCATENATE([Store], [Date]).
  2. Create the same Mixed Key in sales data-set; inspect types and matching values.
  3. Remove the automatically inferred Features–Stores relationship if it does not represent the intended grain, then relate Features Mixed Key to Sales Mixed Key.
  4. Keep the Stores–Sales Store relation, and follow the LMS instruction for how filters should travel and which security option to select.
Inputs: Features data set.csv · sales data-set.csv · stores data-set.csv.

Knowledge-check behaviour

Test the model with a simple chart: select a Store and compare the Features context with Sales totals. The filter should behave as you described it.

For this exercise: Mixed Key is the bridge used by the LMS. Do not assume that joining text this way is right for every project.
